# 19. 플러그인 아키텍처 (R09)

## 1. 플러그인 유형과 포인트

| 유형 | 확장점 | 예 |
|---|---|---|
| parser | DPI 파서 등록(`06` §6) | 신규 프로토콜 식별 |
| signature | 시그니처 규칙 공급자 | 사용자 정의 탐지 |
| auth | 인증 방법(`10` §2) | 새 인증 백엔드 |
| log-sink | 이벤트 싱크(`12` §1) | SIEM 커넥터 |
| policy-action | verdict 후처리 | 외부 시스템 연동 |
| service | 네트워크 서비스 확장(`09`) | 특수 DHCP 옵션 |

## 2. ABI/로딩

- 형식: 공유 라이브러리(`dlopen`, libc 기능) 또는 정적 링크(빌드 타임 등록).
- 계약: 버전화 ops 구조체(`struct ngfw_plugin_ops`), 필드: `api_version`, `type`, `name`,
  `caps`, 각 유형별 ops. 로더는 미지원 api_version 거부(협상 없음 — 명확성 우선).
- 매니페스트: `plugin.json`(이름/버전/유형/의존성/서명 해시), 로더가 검증.
- 안전 규칙: 기본 경로에서만 로드(설정된 디렉터리), 서명 검증 옵션(기본: 해시 기록), 크래시는
  프로세스 격리로 완화(파서 플러그인은 엔진 프로세스 내 실행 — 엔진 재시작 절차 `02` §9).

## 3. 정적 vs 동적 정책

- 코어 기능은 정적 내장(기능 보장), 확장성 요구는 동적 플러그인(R09). 배포 기본 세트는 정적
  빌드에 포함(사용자 혼란 최소화).

## 4. 버전 관리

- 플러그인 ABI 마이너 증가: 하위 호환 추가 필드만. 메이저 증가: 파괴적 변경, 코어 동시 업그레이드.
- `ngfw plugin list/verify` 명령 + selftest: 로드/언로드/ABI 협상/크래시 격리.
